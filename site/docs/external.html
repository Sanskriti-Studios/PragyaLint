External packages & frameworks

PragyaLint analyzes your code — the files under the root you point it at. The third-party packages you import (sympy, PyQt5, Django, numpy, …) are treated as opaque leaves in the module graph: never scanned, never imported, and never flagged. Here's exactly how that works and what it means for real projects.

External packages are opaque leaves

Discovery walks only the target directory and skips site-packages, .venv, venv, node_modules, and __pycache__. So site-packages/sympy/… is never traversed, parsed, or reported on. When a file says 

import sympy
from PyQt5 import QtCore, QtWidgets

the resolver can't find sympy or PyQt5 under your root, so it records them as external dependency edges — real import usage that keeps the importing file reachable, without following the package's internals.

Nothing is imported or executed

The whole analysis is built on the stdlib ast module. PragyaLint never calls import on your modules, never spawns your __init__.py side effects, and never touches a virtualenv. The practical upshot:

  • A scan succeeds even if none of your third-party dependencies are installed — no pip install required for an accurate analysis.
  • Package-level effects (Django app registry, Qt event loops, numpy import time) can't crash or corrupt the analysis.

Framework entry points

Whatever framework you use, the entry files work the same way — see Entry files for the full rules. The conventional entries cover the common GUI/CLI shapes automatically:

For anything else, point at an explicit entry: 

pragyalint -r . --entry manage.py --entry bot.py

What still gets flagged

Being external doesn't exempt a file from the normal rules:

  • An import that's genuinely unused in a reachable file is still a finding — import numpy you never use in that module is dead regardless of numpy being third-party.
  • Your own modules that nothing reaches are still unused_file HIGH findings — the graph treats your code and the vendor's code differently for a reason.

Framework magic & dynamic dispatch

ORMs, declarative widgets, and plugin frameworks call names reflectively (Django model fields, Qt meta-objects, decorator registration). PragyaLint recognizes dispatch tables, getattr(), and decorator references as real usage — see Dynamic dispatch. When it detects a pattern it can't resolve (computed getattr names, exec), it downgrades the remaining findings project-wide to LOW confidence and refuses to auto-delete without --force, so framework magic can't silently lose a symbol that's actually alive.

Go further with plugins

If a framework has conventions worth a dedicated rule, write a custom finder via the Plugins API — it gets the same module graph and ast trees, so it can reason about your framework exactly like the built-in rules reason about plain modules.
